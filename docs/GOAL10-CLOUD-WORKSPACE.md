# Goal 10 — Cloud Workspace (private project backup)

Status: implementation is on the isolated goal10-cloud-workspace branch. Production and the live Supabase database have not been changed by this feature.

## Why this is separate from GitHub

GitHub stores the Geed Hardwin application source code and its migrations/tests. It is not a customer file store. Project JSON, artwork, fonts, audio and exports must never be committed to the application repository or Git LFS.

The design follows the common SaaS split:

- Supabase Postgres stores the account owner, project name, schema version, object key, saved size, checksum, and cloud version.
- Cloudflare R2 stores the actual project snapshot as a private object.
- The object key is generated by the server as user-id/project-uuid/snapshots/reservation-id.json. The browser never chooses another user's object path.
- The browser asks the Vercel API for a short-lived URL, then sends the file directly to R2. R2 access credentials stay in server environment variables.
- Local IndexedDB autosave and JSON export remain available. Cloud saving is an explicit action; no silent background sync or cloud deletion is introduced.

## First release scope

The editor's existing projectSnapshot() already packages scenes, layers, keyframes, symbols, resource-library images/fonts, and embedded image/audio data URLs. Version 1 stores that complete snapshot as one JSON object so the current project format remains unchanged.

- Manual save to cloud and open from cloud.
- One current cloud snapshot per project. Each successful overwrite increments a metadata version counter.
- Maximum single object size defaults to 50 MiB (server-enforced).
- Per-account total quota is read from entitlements.cloud_storage_limit_bytes.
- New accounts and the existing test account currently have a zero-byte cloud allowance, so cloud uploads remain disabled until the owner approves and sets a specific limit.
- Quota is reserved under a database row lock before issuing an upload URL. The database finalization records the new object pointer and byte count only after the server verifies the uploaded object with a signed HEAD request.
- Project metadata write access is revoked from browser clients; writes go through service-role-only RPCs.
- The browser verifies SHA-256 after download before loading a project.
- Cloud storage errors never delete or overwrite the local autosave.

## Server environment variables

Set these in Vercel Preview only after enabling R2 and creating a private bucket. Never put values in source control, frontend code, localStorage, browser-visible build variables, or chat.

Supabase:
- GEED_SUPABASE_URL
- GEED_SUPABASE_PUBLISHABLE_KEY
- GEED_SUPABASE_SERVICE_ROLE_KEY (server-only)

Cloudflare R2:
- GEED_R2_ACCOUNT_ID
- GEED_R2_BUCKET
- GEED_R2_ACCESS_KEY_ID
- GEED_R2_SECRET_ACCESS_KEY (server-only)

Optional:
- GEED_CLOUD_MAX_OBJECT_BYTES (defaults to 50 MiB; accepted range 1 KiB–100 MiB).

## Cloudflare setup still needed

R2 is not enabled on the connected Cloudflare account yet; the API currently returns Cloudflare error 10042, "Please enable R2 through the Cloudflare Dashboard."

1. Open the Cloudflare R2 dashboard: https://dash.cloudflare.com/?to=/:account/r2/overview
2. Enable R2.
3. Create a private bucket named geed-hardwin-user-data.
4. Create an R2 API token with Object Read & Write, scoped to that bucket only.
5. Configure bucket CORS for the exact production and Vercel Preview origins. Allow GET, HEAD, PUT, and DELETE; allow the required Content-Type header; expose ETag.
6. Enter the R2 and Supabase secrets directly in Vercel Project Settings → Environment Variables, Preview environment only. Do not share the Secret Access Key in chat.

No bucket or token has been created by this branch. The application code does not require a public bucket or a paid app plan. Cloudflare may require account-level R2 activation or billing onboarding before issuing API tokens; do not accept any checkout or paid commitment without reviewing its terms first. Review the live Cloudflare/Supabase pricing before opening this to public users; free quotas can change.

## Remaining validation before release

- Enable R2 and supply Preview environment variables.
- Apply the migration to a non-production/test database first.
- Set a deliberate test-account cloud quota; do not grant a quota to all users by default.
- Validate save, reopen from another browser/device, SHA-256 mismatch, over-quota rejection, expired URL, and two-account isolation (account B must not list, read, overwrite, or delete account A's project).
- Confirm the current Supabase free storage and provider limits against expected use.
- Do not merge to main or deploy Production until these checks pass and the owner explicitly approves release.

## Later improvements

If snapshot sizes or upload times become excessive, split resource blobs from the project document and deduplicate immutable assets by checksum. Add project history/retention only after the storage impact is measured. Do not add real-time collaborative editing (e.g. Yjs) unless simultaneous multi-user editing becomes an actual product requirement.
